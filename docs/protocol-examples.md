# Data Communication Protocol Examples

This document contains **examples for discussion and experimentation only. It is not the team's agreed implementation protocol.** UART settings, JSON formats, field names, topics, and transmission intervals may change during implementation. The sender and receiver developers should agree on the protocol before using it and update this document when decisions change.

## 1. STM32 ↔ NodeMCU: UART

- Suggested initial configuration: `115200 baud, 8N1`. Use matching settings on both boards.
- Send UTF-8 JSON, one message per line, terminated by `\n`. The receiver must buffer incoming data until a complete line is available before parsing it.
- Suggested maximum message size: 512 bytes, including the newline. If a line contains invalid JSON or exceeds the limit, discard it and wait for the next message.
- Select the UART instance and pins from the actual board pin maps. Connect TX → RX, RX → TX, and a common GND. Check the voltage levels against the board documentation.
- Keep debug logs off the UART channel used for JSON messages.

Example status message from STM32 → NodeMCU, using 12-bit ADC readings and RGB values from 0–255:

```json
{"v":1,"type":"telemetry","boot_id":"boot-01","seq":12,"joy_x":2048,"joy_y":1800,"button":0,"led_r":0,"led_g":0,"led_b":255,"mode":"local"}
```

Example command from NodeMCU → STM32:

```json
{"v":1,"type":"command","command_id":"cmd-001","action":"set_rgb","r":0,"g":0,"b":255}
```

Example acknowledgment after the STM32 successfully applies the command:

```json
{"v":1,"type":"ack","command_id":"cmd-001","ok":true}
```

Use `button: 1` for pressed and `0` for released. Member 1 should normalize the hardware's active-low or active-high signal accordingly. Increment `seq` for each message and restart it after a reboot. Change `boot_id` for each boot; one option is to have the NodeMCU generate it and provide it during a handshake.

## 2. NodeMCU ↔ NETPIE ↔ Backend: MQTT

Example topics for communication between the device and backend:

| Topic | Sender → Receiver | Purpose |
| --- | --- | --- |
| `@msg/game/device-01/telemetry` | NodeMCU → Backend | Current device status |
| `@msg/game/device-01/events` | NodeMCU → Backend | Game events, such as a player submitting an answer |
| `@msg/game/device-01/commands` | Backend → NodeMCU | Start a round, change modes, or control the LED |
| `@msg/game/device-01/acks` | NodeMCU → Backend | Acknowledge command execution by the STM32 |

Configure the NodeMCU and backend as separate NETPIE Devices with distinct ClientIDs, in a Group that allows them to communicate. Each client should use its own credentials. Do not use the same MQTT ClientID for simultaneous connections.

The NodeMCU updates the latest device state through NETPIE's `@shadow/data/update` topic, wrapping the payload as follows:

```json
{"data":{"joy_x":2048,"joy_y":1800,"button":0,"mode":"local"}}
```

As a starting point, send telemetry/Shadow updates once per second for monitoring and send game events immediately when they occur. Avoid uploading every ADC sample. Adjust the transmission rate to match the game's needs and the applicable service quota.

Example event generated by the STM32 and forwarded by the NodeMCU:

```json
{"v":1,"type":"answer","device_id":"device-01","game_id":"game-001","round_id":1,"event_id":"game-001-r1-a1","direction":"left","reaction_ms":320}
```

Example backend handling: validate `game_id`, `round_id`, and `event_id` to accept events only for the active round and reject duplicates. Receiving messages through MQTT does not automatically prevent duplicate score records. The team must define this behavior when implementing the game.
